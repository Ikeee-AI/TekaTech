# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Commands

**Backend** (from `backend/`, Python 3.12+ with [uv](https://docs.astral.sh/uv/)):
```bash
uv sync                                   # install deps
uv run uvicorn main:app --reload          # dev server on :8000
uv run pytest                             # full suite
uv run pytest tests/test_query.py         # one file
uv run pytest -k test_delete_gadget        # one test by name
```

**Frontend** (from `frontend/`):
```bash
npm install
npm run dev      # Vite dev server on :5173
npm run lint     # eslint — must stay clean, see "Lint conventions" below
npm run build
```

Both halves need their own `.env` (neither is committed) — see `backend/README.md` and `frontend/README.md` for the exact keys. The two Supabase keys are **different**: backend uses the `sb_secret_` service-role key, frontend uses the `sb_publishable_` anon key.

## Architecture

### The frontend never queries data tables
Supabase is used from the browser for **auth only** (`src/context/AuthContext.jsx` → `signUp`/`signIn` hit Supabase directly). All data flows through the FastAPI backend: `src/api/client.js` wraps `fetch`, pulls the current Supabase session's `access_token`, and sends it as a `Bearer` header. The backend verifies it with `supabase.auth.get_user(token)` in `auth.py`.

### Route code is the *only* access control
The backend connects with the **service-role key, which bypasses Row Level Security entirely**. Whatever RLS policies may exist in the Supabase project provide zero defense-in-depth here. Every authorization decision lives in the FastAPI dependencies:
- `get_current_user` — any logged-in Supabase user
- `get_current_admin_user` — additionally requires `app_metadata.is_admin`

Admin is a flag on the Supabase auth user's `app_metadata`, which **only** the admin API (service-role key) can set — a user can never grant it to themselves (unlike `user_metadata`, which is client-writable). Promote someone with:
```python
supabase.auth.admin.update_user_by_id(user_id, {"app_metadata": {"is_admin": True}})
```
Admin-only today: create/edit/delete gadgets, upload a gadget photo (`POST /gadgets/{id}/image`: 2 MB, JPEG/PNG/WebP/AVIF by magic bytes, stored in the public Supabase Storage bucket `gadget-images`, which is created by hand from `backend/sql/manual/` and never gets a write policy), ingest/index/delete specs, add/edit/delete benchmarks, web drafts (`POST /gadgets/{id}/web-drafts`), list/resolve corrections, the read-only `GET /admin/overview` (#206) (the catalog is admin-curated since 3 Nov 2026, `docs/scope-changes.md`). Any logged-in user can submit corrections and list their own (`/corrections/mine`), manage their own My Gadgets list (`/me/gadgets`, always scoped to the session user; no user-id parameter), read/clear their saved questions about a gadget (`/me/gadgets/{id}/questions`) or about a set of phones (`/me/comparisons/questions?ids=…`, 2–5 ids in any order), read their own daily AI-question count (`GET /me/ai-usage`), and delete their own account (`DELETE /me/account`: their rows first, then the Auth user; admin accounts are refused). **Since 14 Nov 2026 (owner decision) visitors who are not signed in may only browse the catalog**: every AI, comparison and question endpoint needs a session (`get_current_user`) and answers an anonymous caller 401 `Login required`: `POST /query` and `POST /query/stream` (all modes: single gadget, comparison, catalog-wide, general knowledge; a question about exactly one gadget is saved to the caller's `user_questions` thread, a question about two or more to `user_comparison_questions`; both saves are best-effort and never fail the answer), `POST /comparisons`, `GET /comparisons/{slug}` (shared links need sign-in too) and `GET /stats/trending-questions`. **No auth at all** (deliberately public, rate limit is the only guard): the catalog reads `GET /gadgets`, `GET /gadgets/{id}`, `GET /gadgets/{id}/specs` (spec text is admin-curated public catalog data that the catalog tiles show; reading it needs no session, asking the AI about it does), `GET /gadgets/{id}/benchmarks`, `GET /stats/spec-coverage`, `/health*` and `/version`. An endpoint with no `Depends(get_current_user…)` is public — check for it when adding routes, and classify it in `tests/test_authorization_matrix.py`.

### The database schema is tracked and manually applied
`backend/sql/001_baseline.sql` tracks the five original application tables, `backend/sql/user_gadgets.sql` adds the per-user My Gadgets list, `backend/sql/user_questions.sql` the per-gadget AI conversation, `backend/sql/user_comparison_questions.sql` the per-comparison one (keyed by the sorted gadget ids; a trigger on `gadgets` deletes turns that include a deleted gadget), `backend/sql/gadget_benchmarks.sql` the published benchmarks, and `backend/sql/match_spec_documents.sql` tracks vector retrieval. `backend/scripts/assemble_sql.py` prints all SQL in application order; `docs/database.md` explains setup and compatibility checks for existing databases. SQL is still **hand-applied in Supabase SQL Editor**: nothing auto-migrates production. CI applies it twice to scratch Postgres/pgvector and runs transactional behavior/access checks. If you add DB-side functions, put them in `backend/sql/` and tell the user how to apply them.

### RAG pipeline
Saving (`routers/specs.py`): raw text → `chunk_text()` → `spec_documents` with NULL embeddings and pending status, without an AI call. Separate `POST /gadgets/{gadget_id}/specs/{spec_id}/index` embeds one saved chunk later; provider failure preserves saved text, and content-match checks protect against stale vectors. `embed_texts()` supports batching when called with multiple texts.

Query (`routers/query.py`): embed the question → `match_spec_documents` RPC for nearest chunks (optionally scoped to `gadget_ids`; a scoped question gets the nearest `MATCH_COUNT` chunks whatever their score, because the right snippet ranks first but often scores under 0.5, while an unscoped one keeps `MATCH_THRESHOLD`) → build a **numbered** context block → prompt instructs the model to cite with `[1]`, `[2]` → frontend `AnswerText.jsx` parses those markers into clickable citations that scroll to the matching source card. The prompt text lives in `prompts.py` (with a `PROMPT_VERSION` label, `"v4"` since 24 Nov 2026. v2 (22 Nov) added to v1 a SUITABILITY rule, a careful judgement from cited specs for "can it run Genshin?"-style questions, and a CONVERSATION rule; v3 adds MISSING SPECS (say the asked spec is not stated when only a related measure is) and VARIANT NOT IN THE SNIPPETS (no other variant's value when declining), eval set 24/24 in both runs; v4 adds WORDING (call snippets "the saved specs", no raw field text such as `removable-battery=no`), eval 24 and 23 vs v3's 23 and 23, "snippet" in 3 of 48 answers vs 27. Older versions stay selectable with `build_system_prompt(version=…)`; v1 keeps its pinned SHA). The gadget chat and the compare page's AI panel send their last 5 turns as `history` (3 until 24 Nov 2026) (`HistoryTurn`: question within the question limit, answer cut to 1200 chars with old `[n]` markers removed); they go in the user message after the snippets (`build_user_message`), retrieval embeds the previous question with the new one (`retrieval_text`), and the cache scope includes a digest of them, so a follow-up such as "can it run smoothly?" keeps its subject while facts still come only from that question's snippets; `citations.py` then removes `[n]` markers outside the snippets that were sent and `/query` returns the count as `invalid_citations_removed`; before that, an answer that cited only as `(n)` (no `[n]` at all) has those markers rewritten to `[n]` for valid snippet numbers, so they render as citations. The chat call is capped with `ANSWER_MAX_COMPLETION_TOKENS` (1500) and `ANSWER_REASONING_EFFORT` (`"low"`); a question about exactly one gadget uses `answer_settings()` instead (`"minimal"` reasoning, `verbosity="low"`, benchmarked 22 Nov 2026 in `docs/devops/app-performance.md`: twice as fast on phone pages, while comparisons stay on `"low"` because minimal picked a wrong winner). Every answer carries a `Server-Timing` header (`embed`/`retrieve`/`generate`/`total` ms): gpt-5-mini bills hidden reasoning as output, `/query` is public and the prepaid balance is shared, and an answer that hits the cap (`finish_reason == "length"`) is a 503, never kept as an answer. **Streaming (23 Nov 2026):** the browser asks `POST /query/stream` (same body, auth, `/query` 10/minute budget shared via `limiter.shared_limit(scope="ai-query")`, daily limit, cache, history and validation; `_run_query` is shared). It runs the unchanged pipeline in a thread with the `_stream_sink` context variable set, so only the grounded chat call streams (`_stream_completion`), and sends server-sent events `sources` → `delta`… → (`reset`, when a streamed decline is about to be replaced by a web or general-knowledge answer, so the browser clears it) → `done` (the finished `QueryResponse` plus `server_timing`, which replaces the streamed text, citations cleaned) or `error` (`{status, detail}`: what `/query` would have raised; a cut-off answer's streamed text is replaced by its 503). Text is held until it can't be the `NOT_IN_SPECS` sentinel. A 401/422/429 is plain JSON before streaming. Frontend: `api.askQuestion({…, ...startStream()})` (handlers from `useAiAnswer`, stripped before sending; plain `/query` without them), `AiAnswerResult` shows `StreamingAnswer` (hidden from screen readers) while loading. `/query` itself is unchanged for the evaluator, smoke checks and tests.

**Benchmarks and web search (24 Nov 2026):** `sql/gadget_benchmarks.sql` (manual) stores published game fps and chip scores per gadget, each with a required source link (`routers/benchmarks.py`: public read, admin writes). For a scoped question that mentions performance or games (`_wants_benchmarks`: a strong word such as fps, gaming or a game name always counts, an everyday word such as fast, run or smooth only when the question isn't about charging, the OS, the screen and similar, and a chip name alone never does; the previous turn counts too), up to `MAX_BENCHMARK_SNIPPETS` (12, round-robin across the compared phones) benchmark rows join the retrieved chunks as extra numbered snippets, so they are cited like specs; a lookup failure never fails the answer. `allow_web_search` (off by default) sends a question the specs don't cover to `web_search.py` (OpenAI Responses API `web_search` tool) instead of general knowledge: cited pages become `[n]` sources (`kind: "web"`), `answer_basis: "web"`, capped by `ai_quota.consume_web_search` (`AI_DAILY_WEB_SEARCH_LIMIT` 5/user/day, `WEB_SEARCH_SITE_DAILY_LIMIT` 40/day site-wide); a used-up cap answers `answer_basis: "web_limit"`, and with the flag on only a real web answer is cached (the cache is shared by all users). With the flag on, a grounded reply that cites nothing and says the answer isn't stated also goes to the web. Admins also get `POST /gadgets/{id}/web-drafts` (draft spec lines or benchmarks with links; nothing saved until the admin saves checked drafts through the normal routes), so web text never reaches the grounding context unreviewed.

Optional general knowledge (`allow_general_knowledge`, off by default, #172) is reached two ways. (1) Retrieval (and the keyword fallback) found nothing: `_general_knowledge_answer()` sends only the question to the `GK_PROMPT_VERSION` prompt. (2) Since 15 Nov 2026 (fallback rule `GK_FALLBACK_VERSION`, now `"gkf-v2"`): scoped questions always retrieve chunks, so (1) never fires on the gadget and compare pages; with the flag on, `build_system_prompt(plain, allow_general_knowledge=True)` adds a rule telling the model to reply exactly `NOT_IN_SPECS` when the snippets hold **none** of the answer (a full or partial answer stays grounded and cited; gkf-v2 adds that in a comparison, if any gadget's snippets give the needed information, the answer stays grounded and says it is not stated for the others). `query.py` detects that reply (`_is_not_in_specs`: case-insensitive, ignoring quotes/backticks/asterisks/trailing punctuation) and makes one extra chat call to the GK prompt; without the flag the rule is not in the prompt (flag-off text stays byte-for-byte `PROMPT_VERSION`, pinned by SHA in `test_prompts.py`) and a stray sentinel becomes `NO_MATCHES_ANSWER`. Either way the sentinel is never shown (a token inside a longer answer is removed together with the quotes, backticks or `**` directly around it), the reply is cached as not grounded under the flag's scope (`v1+gkf-v2+gk-v2`) and nothing is written to `query_history`. Evaluate it with GK-08 (must reach GK) and GK-09 (`stays_grounded`: a partly answered comparison), both scoped in `prompts/eval/gk_scope.json`.

Consequence worth knowing: spec text lands verbatim in the LLM's grounding context. Since 3 Nov 2026 only admins can ingest specs, and a user's correction only reaches the context after an admin approves it, so the stored-prompt-injection surface is now admin-reviewed input. Don't reopen ingestion to all users without asking. The system prompt mitigates it by framing snippets as untrusted data; keep that section if you rewrite the prompt.

**The prompt's formatting rules are coupled to `AnswerText.jsx`.** That component renders exactly three things: `[n]` citations, `**bold**`, and `- ` bullets — and bullets only become a list when at most one non-bullet line precedes them and at most one follows (a closing verdict, allowed since 24 Nov 2026). The prompt states those limits deliberately. Loosening it (headings, tables, `[1,2]`-style citations) makes the model emit markup that renders as literal text, with no error to notice. Change both files together or neither.

Comparison mode also passes a "Gadgets in this comparison" note listing every requested gadget, because retrieval only surfaces gadgets that *have* specs — without it the model can't distinguish "no specs on file" from "not in scope" and quietly compares a subset.

### Shared AI panel logic
`AIAnswerPanel` (single gadget) and `AIComparisonPanel` (comparison) differ only in their header and question input. Everything else is shared: `hooks/useAiAnswer.js` (loading/error/result state, plain-language toggle, citation scroll, copy) and `components/AiAnswerResult.jsx` (error block, answer, collapsible sources, footer). Changes to answer rendering or citation behavior belong in those two files, not in the panels.

### Tokens
`tokens.py` owns both tiktoken encodings, because the two models **do not share one**: `text-embedding-3-small` uses `cl100k_base`, `gpt-5-mini` uses `o200k_base`. Count with the wrong one and the number is silently wrong. Use `count_embedding_tokens` for anything headed to `embed_texts`, `count_chat_tokens` for anything headed into a prompt.

Input limits are enforced twice on purpose: a loose character cap (free, rejects the absurd) then a token cap (the real limit). Characters are a poor proxy — measured on real spec text the ratio swings from ~1.5 chars/token (Japanese) to ~4.3 (Filipino), so a char-only cap lets one request cost ~3x another of identical length.

`query.py` records `embedding_tokens` / `prompt_tokens` / `completion_tokens` into `query_history` from the `usage` block OpenAI returns on every response. Those columns only exist after `sql/add_query_history_token_columns.sql` is applied, so the insert retries without them on schema error — and the whole history write is wrapped so it can never fail the request, since both OpenAI calls are already billed by the time it runs.

### Rate limiting
`rate_limit.py` holds a module-level `slowapi` `Limiter`. Applied to `/query` (10/min), spec ingestion, spec indexing, comparison creation and gadget photo upload (20/hr each). **slowapi requires the endpoint to accept `request: Request`** even if unused — omitting it breaks the decorator at runtime, not at import.

On top of that, `ai_quota.py` gives each signed-in **non-admin** user `settings.ai_daily_question_limit` (`AI_DAILY_QUESTION_LIMIT`, default 20) `POST /query` questions per UTC day, resetting at 00:00 UTC = 08:00 Manila; admins (`app_metadata.is_admin`) are exempt. It is keyed on the user id plus the UTC date, because a `limits` fixed window starts at the first hit (a bare "20/day" would reset 24 h after each user's first question). It is counted in the route body, so a 401/422 costs nothing, while cached answers and later 503s do count. Over the limit is a 429 `{"detail": "You've used today's 20 AI questions. They reset at 8:00 AM (Manila time)."}` with `Retry-After`. Non-admin answers carry `X-AI-Questions-Limit` / `X-AI-Questions-Remaining` (CORS-exposed), and `GET /me/ai-usage` returns `{limit, remaining, resets_at}` (all null for an admin). It uses the same counter store as the limiter below, so with `memory://` the counts reset on a redeploy (accepted by the owner).

Counter storage comes from `settings.rate_limit_storage_uri` (default `memory://`). `memory://` is per-process and therefore only correct on a single worker; a shared store (`redis://`) is required for multi-worker/replica deploys. `verify_storage_reachable()` runs in the app lifespan and **aborts startup** if a configured store is unreachable — deliberately no `in_memory_fallback`, since a silent downgrade to per-process counters looks healthy while the protection is gone. Don't "helpfully" add a fallback.

## Testing

`tests/conftest.py` does three things worth knowing before writing tests:
- `fake_supabase` — an in-memory fake of the Supabase fluent builder. Configure per-test with `fake_supabase.set_response(table, operation, data)` where operation is `"select"`/`"insert"`/`"update"`/`"delete"`. RPC calls key off the pseudo-table `"_rpc"` with operation `None`. If a router starts using a builder method the fake lacks (e.g. `.limit()` was added for stats), add it to `FakeQuery`.
- `client` — a `TestClient` that overrides `get_current_user` to return a fake **admin** user. Tests assume an authenticated admin caller. To test a non-admin/anonymous path, override `app.dependency_overrides[get_current_user]` inside the test and restore it in a `finally`.
- `reset_rate_limiter` — autouse; without it the shared limiter would leak hits across tests (they all share one client "IP").

Tests never make real Supabase or OpenAI calls. Mock OpenAI with `unittest.mock.patch("routers.query.client")` (module-level client object) or `patch("routers.specs.embed_texts", ...)`.

## Lint conventions

`npm run lint` is currently clean and should stay that way. Two deliberate patterns:

- **`react-hooks/set-state-in-effect` is suppressed at specific call sites.** The app-wide data-fetching convention is `setLoading(true)` → `api.x().then(...).finally(() => setLoading(false))` inside a `useEffect`, used in ~12 components. The strict rule flags this categorically. Suppress at the line with a comment explaining why; do **not** restructure the fetch pattern in one component only, and do not disable the rule project-wide.
- **`AuthContext.jsx` exports only components.** `react-refresh/only-export-components` forced a three-file split: the provider (`context/AuthContext.jsx`), the raw context object (`context/authContextValue.js`), and the hook (`hooks/useAuth.js`). Don't consolidate them.

## Gotchas

- Both halves need matching config to talk to each other: the frontend's `VITE_API_BASE_URL` must point at the backend, and that frontend's own origin must appear in the backend's `cors_origins`. Vite inlines env vars **at build time**, so changing `VITE_*` requires a dev-server restart or rebuild — it is not read at runtime.
- The backend's allowed CORS origin comes from `cors_origins` in its `.env` (comma-separated, defaults to `http://localhost:5173`). If Vite starts on a different port because 5173 is taken, requests fail CORS until that origin is added.
- A paused Supabase project surfaces as DNS failure then Cloudflare 521, and takes a few minutes to fully wake after resuming — not an app bug.
- `FAILURE_SIMULATION_ENABLED` (the `/query` failure drill, admin + `X-Simulate-Failure` header only) must stay unset in production, except during the supervised, time-boxed drill in `backend/README.md` ("Supervised production drill"), when the DevOps Engineer sets it in the Railway dashboard (API host since 12 Nov 2026) and removes it straight afterwards. Never add it to `render.yaml` or `.railway/railway.ts`; a test fails if it appears there.
